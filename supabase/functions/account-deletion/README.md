# Reviewed account deletion

This is operator-invoked source code; it has not been deployed or tested against live Auth/Storage. There is no automatic cron or app-client permission to process requests.

Apply the privacy migrations, including `20261102000008_reviewed_account_anonymization.sql`, to an isolated staging project first. The migration installs `public.tabby_pre_request` for the current database's `authenticator` role and restrictive authenticated policies for existing public/Storage RLS tables. It fails and rolls back if another nonempty request hook needs composition. Preserve that hook's behavior when composing it; verify that PostgREST reloaded the resulting configuration. Future RLS tables/definer RPCs must retain this lifecycle guard. Test an already-issued token after preparation through REST, Storage and Realtime before considering deployment verified.

Keep default gateway JWT verification enabled. Configure `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY` and a separate `PRIVACY_REVIEW_SECRET` in server secrets. Never put them in Flutter, Git or operator logs. Only after reviewing the exact existing user request, invoke this function over HTTPS with service authorization, the `x-privacy-review-secret` header, and a JSON body containing `request_id` and `reviewed: true`. No account ID is accepted from the caller; the database resolves it from the request. Do not invoke a live request as a test.

The processor records review, bans sign-in, redacts the public profile/owned contacts/private receiving details and method revision snapshots, removes private connection operations, retires push bindings/jobs, redacts owned notification text and cancels pending reminders. It queues only owned `profile-avatars`/`payment-methods` objects for Storage API removal. Each acknowledgement requires that the object no longer exists. Batches are bounded; retry the same reviewed request after `processing` or a transient failure. No provider payloads or object paths appear in responses.

Auth is **soft deleted** with the Admin API. Its deleted identity is retained to preserve existing foreign keys and owned financial proof images. Auth's profile-upsert trigger cannot restore personal profile fields. The database only completes a request after it observes `auth.users.deleted_at`, no remaining Auth sessions and no remaining private-media jobs/objects. A lost Auth reply is resumable without trying to update the deleted account again. Failed or partial work remains `processing`; an HTTP success alone cannot mark completion.

Confirmed transactions, allocations, payments, receipt/proof records and `payment-proofs` images remain unchanged. Stable financial identities and their shared audit descriptions are retained; new shares for an inactive account are rejected. Other participants' existing copies, previously issued signed URLs until expiry, local drafts/recovery archives and provider-managed audit logs are outside this processor's erasure scope. The app discloses retention and export exclusions. This is an implementation retention policy, not a legal compliance or release approval.

Local evidence: `node scripts/test-money-commands.cjs`, `node scripts/test-backend-native.cjs`, and `node --test scripts/test-account-deletion-worker.mjs scripts/test-account-deletion-transport.mjs`. SQL fixtures inject Auth claims and simulate Auth/Storage state changes; the transport fixture mocks HTTP and loads the TypeScript entry point under Node. Neither is a deployed Deno gateway/provider test. Full fresh/upgrade provisioning, sign-in/refresh denial, staging hook reload and physical-device flows remain unverified.
