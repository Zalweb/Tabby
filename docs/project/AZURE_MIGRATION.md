## Architecture and cost decision

Tabby uses Supabase PostgreSQL, Auth, PostgREST, Storage, Realtime and Edge functions. Azure Database for PostgreSQL or Cosmos DB alone cannot replace that contract. [DEC-012](DECISIONS.md#dec-012--stage-the-full-supabase-backend-on-azure-before-cutover) selects a single Ubuntu Azure VM with the pinned official self-hosted Docker stack, HTTPS and persistent SSD. The destination is now deployed; see [operations/source](../../deploy/azure-full/README.md) and [execution evidence](../verification/VER-QA-002-AZURE-FULL.md). It has single-host availability limits and needs maintenance. A separate protected database backup/restore and media import are still required before cutover.

Supabase's current documented minimum is 2 CPU cores, 4 GB RAM and 40 GB SSD; recommended capacity is 4 cores, 8 GB RAM and 80 GB SSD. Tabby needs Auth, Storage, Realtime and functions, so those services cannot simply be removed to fit a tiny free VM. Price and student quota must be checked for the selected region/SKU, disk, public IP, backups, egress and any logging or secret service. No claim is made that the complete backend is free or fits twelve months of hosting within USD 100. Source: [Supabase self-hosting requirements](https://supabase.com/docs/guides/self-hosting/docker).

Use an explicit spending plan against **remaining** credit after any existing Azure usage. Set actual/forecast alerts at USD 25/50/75/90 against the approved period and verify the subscription currency. Budget alerts do not stop consumption and can lag; they are not a hard USD 100 cap. Confirm the student subscription spending limit remains enabled and do not convert to paid billing. Microsoft states services/subscription are disabled when student credit is exhausted. Rehearsal machines can be deallocated outside test windows, but disks/IP/backups may still cost money. Do not schedule automatic shutdown of the production backend. Sources: [Azure budgets](https://learn.microsoft.com/en-us/azure/cost-management-billing/costs/tutorial-acm-create-budgets), [student credit behavior](https://learn.microsoft.com/en-us/azure/cost-management-billing/manage/azurestudents-subscription-disabled).

## Migration sequence

1. **Inventory without mutation.** Recheck live PostgreSQL version, extensions, migration history and drift; catalog effective grants/RLS, Auth providers/hooks, buckets and object inventory, Realtime publications, functions, schedulers and private secrets configuration. The November 5 record found 18 deployed migrations while this repository contains 50 files, with version drift. That is historical evidence, not today's inventory. Reconcile each history row by version and actual statements; never blindly replay all files or rename applied migrations.
2. **Rehearse to an isolated destination.** Provision the cost-reviewed Azure stack with a pinned Supabase release, compatible PostgreSQL and extensions, persistent encrypted disks and separately protected backup storage. Keep application writers and schedulers disabled. Restore following the official platform-to-self-hosted procedure; account for managed roles, ownership and schema conflicts rather than assuming an unmodified platform SQL dump imports into a different Supabase version. Encrypt exports outside Git and restrict access. Source: [restore from Supabase Platform](https://supabase.com/docs/guides/self-hosting/restore-from-platform).
3. **Copy media separately.** Database Storage rows contain metadata, not receipt/avatar/QR file bytes. Copy objects through the documented Storage/S3 protocol rather than placing downloaded files in the self-hosted data directory. Verify bucket/object counts, paths, sizes and checksums against a stable source inventory. Preserve object ownership and access policies; reconcile metadata changes introduced by copying. Reissue signed URLs on destination. Source: [Supabase Storage migration](https://supabase.com/docs/guides/self-hosting/copy-from-platform-s3).
4. **Upgrade and configure.** Apply only reconciled pending Tabby migrations on the restored destination and record exact versions, commit and schema inventory. Verify the pair helper no longer exposes unchecked access, configure lifecycle hooks without overwriting existing hooks, restore SMTP/OAuth/callback allowlists, deploy the three functions and their secret/scheduler configuration, and verify gateway authentication. Keep all M2 flags false. Keep recurrence/push/deletion processing paused until duplicate side effects are prevented.
5. **Validate data and service behavior.** Compare immutable user/ledger/payment/audit IDs and row counts, integer-centavo allocations/balances, foreign keys, original confirmed history and object checksums. Use dedicated synthetic accounts for actual Auth-issued positive/negative RLS and Storage tests, payment concurrency/idempotent response-loss journeys, Realtime, OAuth, email recovery, reviewed deletion and provider acceptance. Ensure tests cannot mutate migrated real users or financial rows. Run [USB live checks](USB_TESTING.md) on the restored endpoint. A smoke pass alone cannot close migration acceptance.
6. **Final synchronization and cutover.** Record a consistent source backup during an agreed write freeze; reconcile final database and object deltas to avoid losing writes made after rehearsal. Validate the new endpoint through a test build first. Then perform the authorized production client/configuration rollout, preventing old and new deployments from accepting divergent financial writes. Announce necessary reauthentication through the existing release/support process; no user messages are sent by this preparation.
7. **Rollback and observation.** Retain protected source/export until the agreed validation period ends. A rollback after destination writes requires an audit-preserving reconciliation of those writes; simply routing users back can lose financial history. Never delete the old project or overwrite confirmed records as a shortcut. Record live environment, applied versions, exact app artifact and acceptance evidence in QA-001/REL-001 before closing release gates.
