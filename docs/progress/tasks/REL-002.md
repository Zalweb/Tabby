## Scope and acceptance

Installed v1.0.4+23 builds embedded the Azure migration VM origin (`tabby-7abf436e-20261113.eastasia.cloudapp.azure.com`). Once AZ-002 deallocated that VM, Android showed a "site can't be reached" error and the iOS app spun during Google sign-in. The managed Supabase project already hosts the production backend and is OAuth-ready, so the fix is to ship builds that compile in the managed production URL/key instead of the Azure origin.

Acceptance: an Android release APK and an unsigned iOS sideload IPA both embed `https://ziaqrkagsvozhotremsx.supabase.co` with the unchanged Google client identifiers, keep package/version/signing/16 KB properties, and are published as `v1.0.4+24` so the landing download hub serves them through `releases/latest`. Runtime Google sign-in on physical devices remains a separate required check and is not claimed here.

## Implemented

- Production readiness probes (2026-11-18): `/auth/v1/health` returned GoTrue `v2.198.0`; `/auth/v1/settings` returned `google: true`, `email: true`, `disable_signup: false`; `/auth/v1/authorize?provider=google&redirect_to=io.supabase.tabby://login-callback` returned HTTP 302 to `accounts.google.com` with the existing Web client ID and `redirect_uri=https://ziaqrkagsvozhotremsx.supabase.co/auth/v1/callback`; `/rest/v1/users` returned an empty set, so the wiped production dataset is intact.
- Android: built the release APK from the current working tree (HEAD `a7394bdfb5bdae53c8a24bec6f1d8addd32abae9` plus preserved concurrent uncommitted work) with `--build-number=24 --target-platform=android-arm64,android-x64 --target=lib/main.dart --dart-define-from-file=.dart_tool/readiness/qa041-prod-public-client.json`. The dart-define file contains only public client fields (production URL/publishable key plus public Firebase values); no private material was written to the repository.
- iOS: created isolated worktree/branch `codex/ios-prod-20261118` at the locked CI source (`70ab9f32...`), repinned `ios/client-config-hashes.json` to the production URL/key SHA-256 values (Google iOS/Web client IDs unchanged), updated `ios/build-source-manifest.json` with the new hash-file digest and a `production_rebind` note, committed as `921e22779fad45144be16fad265dcd7643122aee`, and pushed the branch. `python scripts/ios-prepare.py --verify-source` verifies all 952 frozen source hashes on that commit.
- CI: updated the repository secret `TABBY_IOS_BUILD_CONFIG` to the four production public fields (values not recorded), dispatched `build-ios.yml` run [44274221017](https://github.com/Zalweb/Tabby/actions/runs/44274221017) on the branch with `build_number=24`. Source verification, locked packages, client-config hash enforcement, CocoaPods install and platform regressions all passed before the native simulator smoke and unsigned archive steps.
- Regression: full `flutter test --no-pub` on the shipped Android source tree passed 1152/1152; `flutter analyze --no-pub lib` reported no issues (62.1 s).
- Publication: GitHub release [`v1.0.4+24`](https://github.com/Zalweb/Tabby/releases/tag/v1.0.4%2B24) carries `Tabby.apk`, `Tabby.ipa` and the versioned `Tabby-v1.0.4+24.apk`/`Tabby-v1.0.4+24.ipa` copies. `landing/app.js` resolves the newest non-prerelease through the GitHub API and rewrites every download link, version tag, size, filename and date, so the landing hub serves this release without a static-page edit; the static fallback text and line-ending-only concurrent landing changes were deliberately left untouched.

## Remaining and unverified

- No physical Android or iPhone Google sign-in was executed after the rebind. The Android build was not installed over v23, so upgrade/data preservation is unverified. The iOS IPA is unsigned and was not signed or launched through Sideloadly.
- The Android APK source is the shared dirty working tree (HEAD plus concurrent uncommitted changes), not an exact clean committed candidate; the iOS IPA source is pushed commit `921e227` only. This is a user-directed downloadable test build, not the official release candidate.
- The official publication contract in [docs/releases/README.md](../../releases/README.md) is not satisfied: no `docs/releases/<commit>.json` candidate record exists, and REL-001, QA-001, physical-device, OAuth, 16 KB runtime and independent integration gates remain open.
- The Azure VM was left running for owners of legacy builds to test against; decommissioning is a separate decision now that new builds no longer depend on it.
